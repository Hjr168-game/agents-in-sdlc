프로젝트에 작은 기능을 추가하는 것으로 시작했습니다. 더 큰 변경에는 더욱 견고한 프로세스가 필요합니다. GitHub Copilot app은 조직의 기존 흐름에 맞춰 올바른 대상을 올바른 방식으로 구현하도록 설계되었습니다. 이 레슨부터 여러 레슨에 걸쳐 일반적인 에이전트 기반 개발 프로세스를 따릅니다. 이슈에서 새 기능을 시작하고, 코드가 유효하고 기능이 예상대로 동작하는지 확인한 다음, 프로젝트에 성공적으로 병합합니다.

> [!NOTE]
> 기능 워크플로를 이어 가는 동안 같은 세션을 사용합니다. 일반적으로는 파일 유형에 따라 세션이나 PR을 나누지만, 여기서는 핵심 개념에 집중할 수 있도록 단계를 간소화합니다.

이 레슨에서는 다음 작업을 수행합니다.

- GitHub 이슈에서 새 에이전트 세션을 시작합니다.
- **Plan** 모드에서 요구 사항을 정의합니다.
- **Autopilot** 모드로 새 기능을 구현합니다.
- 코드를 검토합니다.
- 브라우저 캔버스에서 기능을 직접 검증합니다.

이 기능을 계속 개발하면서 리포지토리 지침을 업데이트하고, 기존 `quality-checks` 스킬을 사용자 지정하고, MCP 검증을 추가하고, QA 에이전트를 만든 다음 기능 PR을 엽니다.

## 시나리오

Tailspin Toys의 카탈로그가 커지면서 방문자가 카테고리와 퍼블리셔로 게임을 좁혀 볼 수 있어야 합니다. 백로그 이슈에 기능이 설명되어 있지만 여러 카테고리를 결합하는 방법과 같은 세부 사항은 코딩 전에 합의해야 합니다. Plan 모드에서 결정을 정리한 다음 범위가 정해진 구현을 Autopilot으로 승인합니다.

## 배경

AI 코딩 에이전트를 개발 흐름에 도입해도 기본 원칙은 달라지지 않습니다. 오히려 더 중요해집니다. 대부분의 개발자는 다음과 비슷한 흐름을 따릅니다.

1. 수행할 작업의 세부 정보가 담긴 이슈를 엽니다.
2. 구현할 항목을 계획합니다.
3. 코드를 작성하고 검토합니다.
4. 테스트를 실행해 코드를 검증합니다.
5. 새 기능을 직접 검증합니다.
6. 풀 리퀘스트(PR)를 만듭니다.
7. 코드를 검토하고 지속적 통합이 성공하면 변경 내용을 병합합니다.

> [!NOTE]
> 정확한 절차는 팀과 조직에 따라 다르지만, 대부분 위 흐름을 변형해 사용합니다.

이 표준 접근 방식을 따르면 AI가 생성한 코드가 요구 사항을 충족하고 사람이 작성한 코드와 동일한 검증 과정을 거치도록 할 수 있습니다.

## 세션 모드

**세션 모드**는 에이전트의 자율성을 제어합니다. 프롬프트 필드 아래의 드롭다운에서 모드를 설정하고 언제든지 변경할 수 있습니다.

- **Interactive**: 사용자와 에이전트가 함께 작업합니다. 에이전트는 변경을 제안하고 진행하기 전에 사용자의 입력을 기다립니다.
- **Plan**: 에이전트가 먼저 계획을 만듭니다. 실행 전에 계획을 검토하고 승인합니다.
- **Autopilot**: 에이전트가 사용자 입력을 기다리지 않고 코드를 작성하고 테스트를 실행하며 반복적으로 개선합니다.

**Plan** 모드에서 시작해 계획을 검토한 다음 **Autopilot**으로 구현합니다.

## 이슈에서 세션 시작

시작하기 전에 별점 PR이 병합되었고 로컬 `main`이 최신 상태인지 확인합니다.

1. 사이드바의 **Sessions** 아래에서 Tailspin Toys 리포지토리 폴더를 선택한 다음 리포지토리의 위쪽 탐색에서 **Issues**를 선택합니다. 기존 이슈인 **Allow users to filter games by category and publisher**를 엽니다. 이미 생성된 이슈이므로 새 이슈를 만들 필요가 없습니다.
2. **New session**을 선택하고 업데이트된 `main`을 기반으로 하는 **new working tree**를 선택합니다.

    ![New session 버튼을 화살표로 가리키는 GitHub Copilot app 이슈 보기](../../../_images/app-new-session-from-issue.png)

3. 이슈가 세션에 연결되었는지 확인하고 모드 선택기에서 **Plan**을 선택합니다.

> [!NOTE]
> Node.js 또는 npm을 찾을 수 없다면 에이전트에 `node --version`과 `npm --version`을 실행하도록 요청합니다. 터미널에서는 실행되지만 세션에서 실행되지 않는다면 앱의 PATH 또는 버전 관리자 설정을 확인한 다음 앱을 완전히 종료하고 다시 엽니다. 실패한 작업과 검사를 다시 시도합니다. 에이전트가 npm을 찾지 못한다는 이유만으로 npm을 다시 설치하지 마십시오.

## 필터링 기능 계획

계획을 세우면 Copilot이 코드를 작성하기 전에 접근 방식을 검토할 수 있습니다. 이슈에서 시작했으므로 Copilot은 이미 기능 요청을 컨텍스트로 갖고 있습니다. 다음 내용을 보냅니다.

```plaintext
Build this feature.
```

Copilot의 질문에 답하고 계획을 이슈의 수락 기준과 비교합니다. 카테고리 및 퍼블리셔 필터링, 접근성 있는 컨트롤, 데이터 액세스 변경, 테스트가 포함되었는지 확인합니다. 여러 카테고리를 결합하는 방법이나 일치하는 게임이 없을 때의 동작처럼 불명확한 사항을 논의합니다.

계획에는 프로젝트의 기존 도구를 사용하는 린트, 단위 테스트, E2E 테스트, 타입 검사가 포함되어야 합니다. 필터링 기능 구현과 테스트에 집중하고, 품질 워크플로를 완료한 다음 PR을 만듭니다. 계획을 승인하기 전에 필요한 변경을 요청하고, 이후 검증에 사용할 이슈 URL과 합의한 추가 사항을 기록해 둡니다.

## Autopilot 명시적 승인

계획이 만족스러우면 **Approve and implement this plan** 또는 사용 중인 버전에 해당하는 옵션을 선택합니다. 승인하면 모드도 자동으로 바뀐다고 가정하지 말고 현재 모드를 확인합니다. 모드 표시기에 **Autopilot**이 표시되는지 확인합니다.

Copilot이 구현을 시작합니다. 수립한 계획을 따라 코드를 생성하고 테스트를 실행하며 결과를 반복해서 개선합니다.

> [!NOTE]
> 승인하면 구현이 즉시 시작될 수 있으므로 먼저 계획을 검토합니다. Copilot이 누락된 종속성이나 포트 충돌을 보고하면 검사가 완료된 것으로 간주하기 전에 설정 문제를 해결합니다. 직접 시작한 서버만 중지합니다.

## 구현 검토 및 검증

생성한 코드도 다른 코드와 마찬가지로 병합 전에 검토해야 합니다. 코드와 사이트를 살펴보고 문제가 없는지 확인합니다.

1. **Changes**를 열고 필터링 구현과 테스트를 살펴봅니다.
2. 여러 카테고리와 퍼블리셔 조합을 포함해 결과를 이슈 및 승인한 추가 합의 사항과 비교합니다. 변경 내용이 기존 리포지토리 지침을 따르는지 확인합니다.
3. 린트, 단위 테스트, E2E 테스트, 타입 검사 결과를 확인합니다. 건너뛴 검사는 통과가 아닙니다.
4. 구현을 수락하기 전에 실패를 해결하고 관련 검사를 다시 실행합니다. Playwright E2E 구성은 미리 보기를 빌드하고 제공하며 로컬 서버를 재사용할 수 있습니다. 테스트한 서버가 이전 레슨이 아니라 이 워크트리에서 시작한 서버인지 확인합니다.

## 새 기능 살펴보기

코드가 괜찮아 보여도 실제로 실행되는지 확인해야 합니다. 이전처럼 앱을 시작하고 브라우저 캔버스에서 사이트를 엽니다.

1. 다음 프롬프트를 사용해 Copilot에 앱을 시작하고 브라우저 캔버스에서 페이지를 열도록 요청합니다.

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. 잠시 후 앱이 시작되고 Copilot app 안에 브라우저 창이 열립니다.
3. 카테고리를 선택하고 결과가 해당 카테고리와 일치하는지 확인합니다. 필터를 지운 다음 퍼블리셔를 선택해 결과를 확인합니다.
4. 카테고리와 퍼블리셔 필터를 함께 적용하고 결과를 이슈 및 승인한 계획과 비교합니다. 여러 카테고리가 지원된다면 합의한 결합 방식도 확인합니다.
5. 일치하는 게임이 없는 조합을 시험하고 빈 상태를 확인합니다. 필터를 지우거나 초기화해 전체 목록이 다시 표시되는지 확인합니다.
6. 확인을 마치면 다음 프롬프트를 사용해 Copilot에 이 세션에서 시작한 개발 서버를 중지하도록 요청합니다.

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 다음 레슨을 위해 이 세션 유지

아직 필터링 PR을 만들거나 병합하지 마십시오. 레슨 4~8에서 사용할 세션, 워크트리(worktree), 브랜치를 유지합니다. 다음 레슨에서는 필터링 코드에 사용자 지정 지침을 적용한 다음 스킬과 QA 개선 사항을 추가하고 레슨 8에서 모든 변경 사항을 포함한 PR을 만듭니다. 개발 서버를 중지한 뒤 세션을 유휴 상태로 둘 수 있으며 다음 레슨에서 같은 세션으로 돌아옵니다.

## 요약 및 다음 단계

서로 다른 에이전트 모드를 사용해 기능을 만들고 검토했습니다. 이 레슨에서는 다음 작업을 수행했습니다.

- GitHub 이슈에서 새 에이전트 세션을 시작했습니다.
- **Plan** 모드에서 요구 사항을 정의했습니다.
- **Autopilot** 모드로 새 기능을 구현했습니다.
- 코드를 검토했습니다.
- 브라우저 캔버스에서 기능을 직접 검증했습니다.

다음으로 [사용자 지정 지침][next-lesson]을 사용해 코드 생성 방식을 자세히 살펴보고 문서화된 관행을 따르도록 합니다.
